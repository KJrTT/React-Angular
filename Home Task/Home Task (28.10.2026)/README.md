# RHF + Zod + TanStack Query

Учебный проект по конспекту **Частей 11–12**. Здесь собраны две темы: работа с формами через React Hook Form + Zod и работа с серверным состоянием через TanStack Query. Проект специально сделан минимальным, чтобы каждая концепция из теории была видна в коде и не тонула в лишних деталях.

## Зачем это нужно

Формы на «чистом» `useState` работают, но с ростом количества полей появляются проблемы: каждый ввод перерисовывает всю форму, логика `touched` и `errors` пишется руками, валидация размазана по компоненту, а правила нельзя переиспользовать на бэкенде. RHF решает первые три проблемы за счёт неконтролируемых инпутов и `ref`, а Zod даёт единый декларативный источник правил.

С серверным состоянием похожая история. Ручной `useEffect` + `fetch` не умеет кэшировать данные, страдает от race conditions при быстрых переключениях, требует вручную инвалидировать кэш после мутаций и ничего не знает о том, что данные устарели. TanStack Query берёт всё это на себя: кэш, повторные запросы, инвалидацию, фоновое обновление и retry.

## Стек

| Пакет | Роль |
|---|---|
| `react-hook-form` | неконтролируемые инпуты через `ref`, минимум ререндеров |
| `zod` | декларативная схема валидации |
| `@hookform/resolvers` | `zodResolver(schema)` — мост между RHF и Zod |
| `@tanstack/react-query` | кэш, инвалидация, retry, фоновое обновление |
| `react`, `react-dom`, `vite` | базовый стек |

## Установка и запуск

Склонируйте проект и выполните `npm install`, затем `npm run dev`. Если ставите зависимости с нуля по конспекту, используйте команды из разделов 11.2 и 12.2: `npm install react-hook-form zod @hookform/resolvers @tanstack/react-query`. После установки обязательно перезапустите dev-сервер — Vite кэширует список зависимостей и без рестарта может не увидеть новые пакеты.


## Что реализовано в Части 11

Форма создания пользователя содержит семь полей: имя, email, возраст, роль, пароль, повтор пароля и «о себе». Zod-схема описывает все правила в одном месте. Для возраста используется `z.coerce.number()` — это принципиальный момент, потому что HTML-инпут возвращает строку, даже если у него `type="number"`, и без `coerce` валидация числа не сработает. Для роли используется `z.enum(['admin','editor','viewer'])`, что напрямую соответствует `<select>`.

Кросс-полевая валидация паролей сделана через `.refine(..., { path: ['confirmPassword'] })`. Параметр `path` здесь критичен: без него ошибка «Пароли не совпадают» попадёт в `errors.root` и не будет привязана к полю, из-за чего пользователь её не увидит рядом с нужным инпутом.

В `useForm` передаётся `resolver: zodResolver(userSchema)` и `mode: 'onChange'`. Второй параметр нужен, чтобы `isValid` пересчитывался на лету — иначе кнопка «Создать» не будет активироваться по мере заполнения формы. Из `formState` используются четыре свойства: `errors` для отображения сообщений, `isSubmitting` для состояния отправки, `isValid` и `isDirty` для блокировки кнопки. Кнопка отключена, пока форма невалидна, пока идёт отправка или пока пользователь ничего не менял — это защищает от случайных сабмитов пустой формы.

После успешной отправки вызывается `reset()`, который очищает форму и сбрасывает состояние «изменено».

## Что реализовано в Части 12

`QueryClient` настраивается тремя параметрами по умолчанию. `staleTime: 30_000` говорит, что данные остаются «свежими» полминуты — повторный запрос в этот период не пойдёт. `retry: 2` даёт две дополнительные попытки при ошибке, что особенно полезно на нестабильных сетях. `refetchOnWindowFocus: false` отключает перезапрос при возврате на вкладку — поведение по умолчанию часто удивляет новичков, поэтому в учебном проекте оно отключено.

`PostsList` использует `useQuery` с ключом `['posts']` и функцией `getPosts`. Ключ — это адрес в кэше, поэтому он должен быть уникальным и стабильным. Компонент обрабатывает три состояния: `isLoading` показывает «Загрузка постов...», `isError` показывает сообщение и кнопку «Повторить», вызывающую `refetch`, а успешный ответ рендерит список. Дополнительно показывается индикатор `isFetching` — он отличается от `isLoading` тем, что становится `true` и при фоновом обновлении, когда данные уже есть на экране.

`AddPostForm` использует `useMutation`. Мутации, в отличие от запросов, не запускаются автоматически — их нужно вызывать через `mutate()`. В `mutationFn` передаётся `createPost`, а в `onSuccess` вызывается `queryClient.invalidateQueries({ queryKey: ['posts'] })`. Это ключевой приём: после успешной мутации мы говорим библиотеке, что данные с этим ключом устарели, и `useQuery` автоматически делает новый запрос. Дополнительно поле ввода очищается. Состояние `mutation.isPending` используется для блокировки кнопки и смены её текста на «Создание...».
